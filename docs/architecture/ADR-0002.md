# ADR-0002 — Zero mixins in v1.0.0

- **Status:** Accepted
- **Date:** 2026-07-25
- **Milestone:** M0
- **Required by:** §7.5, §3.5

## Context

Mixins rewrite Minecraft bytecode at load time. They are powerful and they are the single
largest source of cross-mod breakage in the modded ecosystem: two mods injecting into the
same method, an injection point that silently stops matching after a patch release, and
failures that surface as a crash in unrelated code.

NexusCore is administration software. Its value proposition is that a server operator can
install it and trust it. A mod that can be broken by an unrelated mod's mixin, or that
breaks unrelated mods with its own, does not deliver that.

## Decision

**v1.0.0 ships with zero mixins.** Every requirement in the master build prompt is met
using supported NeoForge APIs: the mod and game event buses, Brigadier, the payload
registration event, the configuration system, menus, and capabilities.

No `[[mixins]]` block appears in `neoforge.mods.toml` and no mixin configuration file
exists in the source tree.

## Introducing the first mixin

Adding one is not forbidden forever, but it is not an implementation detail. It requires a
new ADR that covers all five of:

1. Which supported APIs were evaluated and precisely why each is insufficient.
2. The exact target class and method, and an assessment of that target's stability across
   the supported NeoForge range.
3. The failure behaviour when the target is absent or has moved — NexusCore must degrade,
   not crash the server.
4. A compatibility test that fails if the injection point stops matching.
5. The compatibility impact on the mods NexusCore is documented as coexisting with.

## Consequences

- Some behaviours reachable by a mixin are not reachable by NexusCore. Where that blocks a
  requirement, the requirement is recorded as `blocked` in `IMPLEMENTATION_STATUS.md` with
  the specific obstacle named — never silently dropped (§1.3).
- NexusCore imposes no mixin-related load order constraints on other mods.
- The JAR remains loadable on any NeoForge build in the supported range without
  bytecode-level assumptions.
