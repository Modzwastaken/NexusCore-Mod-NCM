# ADR-0004 — Permission precedence

- **Status:** Accepted
- **Date:** 2026-07-25
- **Milestone:** M0 (decision), implemented by `PermissionService` in M3
- **Required by:** §9.2, §9.3

## Context

Every privileged command, GUI action, packet handler, scheduled action, and API mutation in
NexusCore resolves through one evaluator (§9.1). If two nodes can both match a request, the
order in which they are considered decides whether an operator is allowed to ban someone.
That order must be **total** — no ties left to hash-map iteration order — or the same
question will get different answers on different runs, and no operator will be able to
reason about their own configuration.

## Decision

### Specificity score

For a node pattern matching the request:

| Pattern shape | Score |
|---|---|
| `*` | `0` |
| trailing-wildcard (`a.b.*`) | `literalSegments × 2` |
| exact match | `literalSegments × 2 + 1` |

Resolving `nexuscore.command.moderation.ban`:

| Pattern | Score |
|---|---|
| `nexuscore.command.moderation.ban` | 9 |
| `nexuscore.command.moderation.*` | 6 |
| `nexuscore.command.*` | 4 |
| `nexuscore.*` | 2 |
| `*` | 0 |

### Precedence, highest first

1. **Higher specificity score.**
2. **Direct subject node beats group node.** A node attached to a player is an explicit act
   about that player; a group node is policy about a class of players. At equal
   specificity the specific act wins.
3. **Explicit `DENY` beats `ALLOW`.**
4. **Higher group weight.**
5. **Pattern, then source, lexicographically.** This step exists solely to make the order
   total, so repeated evaluation of an unchanged data set is bit-for-bit reproducible.

### Wildcard construction rule

A wildcard is legal **only** as the entire pattern (`*`) or as the final segment
(`a.b.*`). `nexuscore.*.ban` is **rejected at construction time**, not at evaluation time.

Mid-pattern wildcards make "longer path beats shorter" ambiguous: there is no defensible
literal-segment count for a pattern whose segments are interleaved with holes. Rejecting
them at construction means the ambiguity can never enter the data set at all.

### `UNDEFINED`

`UNDEFINED` is never granted. It exists as a distinct value only so that
`/nexus permission check` can tell an operator *"explicitly denied by node X from source
Y"* apart from *"never granted by anything"*. Those two states need different fixes, so
collapsing them into one boolean would make the explain command useless.

## The consequence operators must be told about

Rule 2 sits **above** rule 3. An operator who wants to revoke access from a player holding
a **direct** grant must remove that grant. Adding a group-level deny at equal specificity
will **not** work, because the direct node wins before the deny is considered.

This is a deliberate trade — an admin's explicit act about one player should not be
silently overridden by a policy change to a group — but it is surprising if undocumented.
It is therefore required to appear in **both**:

- `docs/admin/permissions.md`, and
- the output of `/nexus permission check`, whenever a direct node is what decided the
  result.

## Test obligations (M3 exit)

Named unit tests are required for: default-deny · exact-beats-wildcard ·
longer-beats-shorter · deny-beats-allow at equal specificity ·
direct-subject-beats-group · expiry exactly at the boundary · context filtering · group
inheritance cycle rejection · construction-time rejection of mid-pattern wildcards ·
determinism across repeated evaluation of an unchanged data set.
