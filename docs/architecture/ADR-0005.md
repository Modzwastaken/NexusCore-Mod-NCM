# ADR-0005 — One tool for formatting and static analysis

- **Status:** Accepted
- **Date:** 2026-07-25
- **Milestone:** M0
- **Required by:** §17.2, M0 step 6

## Context

§17.2 lists "Static analysis and formatting pass" as a build gate, and M0 step 6 requires
both to be configured before any product logic is written. The usual arrangement is two
tools — a formatter such as Spotless plus an analyser such as Checkstyle, SpotBugs, or
Error Prone.

## Decision

**Checkstyle 10.21.1 alone**, configured from `config/checkstyle/checkstyle.xml`, with
`severity=error`, `maxWarnings = 0`, and `ignoreFailures = false`. It runs against both
`main` and `test` source sets as part of `check`.

The ruleset covers both duties deliberately:

- *Formatting:* `Indentation`, `LineLength`, `FileTabCharacter`, `NewlineAtEndOfFile`,
  trailing-whitespace regex, `LeftCurly`/`RightCurly`, the `Whitespace*` and `*Pad` modules.
- *Static analysis:* `EmptyCatchBlock`, `EqualsHashCode`, `CovariantEquals`,
  `StringLiteralEquality`, `FallThrough`, `MissingSwitchDefault`, `SimplifyBoolean*`,
  `UnusedImports`, `NoFinalizer`, `MutableException`, `IllegalThrows`, `FinalClass`.

Two rules are load-bearing for the truth rules rather than for style:

- **`EmptyCatchBlock`** — §2.1 Rule 4 makes "catching an exception and swallowing it to
  silence a failure" a §1.3 violation. This makes the compiler enforce that.
- **`SuppressWarningsHolder` + `SuppressWarningsFilter`** — suppressions become visible
  and reviewable rather than invisible, since §2.1 Rule 4 also forbids using
  `@SuppressWarnings` to hide a real type or nullability problem.

## Rationale

- **No warning tier.** A warning tier is a place for problems to accumulate unread. Every
  violation fails the build.
- **One tool, one config, one failure mode.** A second tool doubles the ways CI can
  disagree with a developer's machine, and the marginal rule coverage of adding Spotless on
  top of these formatting modules is small.
- **Fewer moving parts on the critical path.** M0's job is to prove the toolchain end to
  end. Each additional plugin is another artifact that has to resolve before a build can
  go green.

## Consequences

- There is no auto-formatter. Checkstyle reports; it does not rewrite. Violations are
  fixed by hand.
- If the ruleset later proves insufficient — nullability analysis and dataflow bug
  detection are genuinely outside Checkstyle's reach — adding Error Prone or NullAway is a
  new ADR, not a silent change.
- The stub-marker gate of §2.4 is **not** part of this: it is a separate Gradle task
  (`stubMarkerCheck`) wired into `check`, because its markers are a project rule rather
  than a Java-language concern.
