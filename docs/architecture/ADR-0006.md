# ADR-0006 — JSON configuration instead of a NeoForge TOML config spec

- **Status:** Accepted
- **Date:** 2026-07-25
- **Milestone:** M1
- **Required by:** §5 ("no duplicate platform frameworks"), §11.1, Appendix C

## Context

§5 says to use NeoForge's own configuration system rather than building a second one, and
Appendix C names `world/serverconfig/nexuscore-server.toml` as the authoritative settings
file. NeoForge supplies `ModConfigSpec`, which produces exactly that.

But Appendix C also names **ten** other configuration files, and every one of them is JSON:
`permissions/groups.json`, `teleport.json`, `moderation.json`, `economy.json`, `shops.json`,
`kits.json`, `scheduler.json`, `themes.json`, and the message catalogues. §11.1 separately
decides that NexusCore's persistent data is structured JSON with atomic replacement.

There is also a functional problem. M1's exit condition requires that a corrupted config
produce a report naming *the file, the key, the invalid value, the expected form, and the
chosen fallback*. `ModConfigSpec` corrects out-of-range values silently by design — it
restores the default and carries on. Getting the five-field report out of it means
re-validating everything afterwards anyway, which is the second configuration system §5 warns
about, just hidden behind the first.

## Decision

**One configuration mechanism: JSON documents in the NexusCore data directory, read through
`JsonStore` and validated by `NexusSettings.validate`.** Settings live in
`<server>/nexuscore/config.json`, alongside the data files.

`ModConfigSpec` is not used, and no `nexuscore-server.toml` is generated.

## Rationale

- **It is one system, not two.** Eleven of the twelve files in Appendix C were always going
  to be JSON. Making the twelfth TOML would have been the duplicate framework, not this.
- **Validation is a first-class result, not a side effect.** `validate` returns a
  `ValidationReport` whose findings carry all five required fields, which is what makes the
  M1 exit condition testable — `ConfigurationServiceTest` asserts on each field by name.
- **Reload is transactional.** The new document is parsed and validated before it replaces
  the live one, so a typo leaves the running configuration untouched and reports why. The
  platform spec has no equivalent guarantee.
- **The data directory is self-contained.** Config, permissions, homes, punishments, and the
  audit log sit together, so a backup is one directory and a support bundle is one archive.

## What this gives up

- No config screen integration. NeoForge can show a `ModConfigSpec`-backed config UI in the
  mods list; a JSON file cannot appear there. NexusCore is server-only through v0.5 and that
  screen is client-side, so the loss is theoretical until M9, and the admin GUI plus
  `/nexus reload` cover the same ground from the server.
- Per-world server configs. `ModConfig.Type.SERVER` is stored per world; NexusCore's
  `config.json` is per server installation. This is the more useful default for an
  administration mod — an operator wants one permission model, not one per world — but it is
  a real difference and is documented in `docs/admin/`.

## Consequences

- Appendix C's `nexuscore-server.toml` row is superseded by `nexuscore/config.json`. This is
  recorded here rather than silently ignored (§1.3, "no silent scope deletion").
- Every configuration document carries `schemaVersion` and `generatedByVersion`, and a change
  to either requires a forward migration under §11.4.
- If a client-side config screen becomes a requirement at M9, the client's *own* settings
  (`nexuscore-client.toml` in Appendix C) may legitimately use `ModConfigSpec`, because those
  are client-owned values with no server authority. That would not reopen this decision.
