# ADR-0007 — Version numbering: v1.0, v1.5, v2.0

- **Status:** Accepted, amended
- **Date:** 2026-07-26
- **Decided by:** the project owner
- **Supersedes:** §3.4 of the master build prompt
- **Amended by:** [ADR-0009](ADR-0009.md) — the third component is a build counter, not a
  patch level. The two lines below that describe patch releases no longer hold.

## Context

The build specification defined a release ladder of `0.1.0` → `0.5.0` → `1.0.0`, where
`1.0.0` was gated on milestone M11: the client mod, the thirteen custom GUI screens, the
economy, the chat system, the scheduler, backups, the benchmark harness, and the public API.

The project owner has decided to ship the current build as **v1.0** and to continue with
**v1.5, v2.0, …**.

## Decision

**Releases are numbered `MAJOR.MINOR.0`, advancing by 0.5 each time:** `1.0.0`, `1.5.0`,
`2.0.0`, `2.5.0`, and so on. Patch releases use the third component (`1.0.1`) and contain
fixes only — no new features and no data-format change.

> **Amended by ADR-0009.** The third component is now a build counter: `1.0.1`, `1.0.2`, …
> are numbered *development builds* on the road to `1.5.0`, and they may add features. Only
> the `x.y.0` shape is a release.

`v1.0` is the first public release. It is not the M11 feature set.

## What this changes, stated plainly

The specification's `1.0.0` meant "feature complete against §22". This project's `1.0.0`
means "the first release the owner considers ready to ship". Those are different claims, and
conflating them would mislead anyone reading the version number.

So two obligations follow, and they are not optional:

1. **`release-notes.md` and `IMPLEMENTATION_STATUS.md` state what is not in the release**,
   in the release itself, not in a separate roadmap. A reader must be able to learn from the
   shipped artifact that there is no economy and no client GUI.
2. **The version number carries no completeness promise.** Nothing in the repository may say
   "1.0 means feature complete", because here it does not.

## Compatibility promise

Semantic versioning applies to **data formats and the command surface**, not yet to a Java
API — there is no public API to promise anything about until M11.

- **MAJOR** (`1.x` → `2.0`) may change data formats, and must ship a forward migration and a
  documented upgrade path (§11.4). It may remove or rename a command.
- **MINOR** (`1.0` → `1.5`) adds features and commands. It may add fields to a data file, but
  reading a `1.0` data directory with `1.5` must work without operator intervention.
- **PATCH** (`1.0.0` → `1.0.1`) fixes defects only. **Amended by ADR-0009:** the third
  component numbers development builds, which may add features. The MINOR promise above
  applies at every rung — a `1.0.x` build must still read a `1.0.0` data directory without
  operator intervention.

Every persistent document carries `schemaVersion` independently of the mod version, so a
data-format change is detectable regardless of which release wrote it.

## Consequences

- The `0.1` / `0.5` labels in the specification are retired. Where documents referred to
  "v0.1 Bedrock" they now say v1.0.
- The milestone names (M0 to M11) remain the internal work breakdown and are still the honest
  measure of feature completeness. `IMPLEMENTATION_STATUS.md` continues to track them, and it
  remains the authoritative record — not the version number.
- The next release is **v1.5**, and the specification's M6 to M8 (economy, chat depth,
  scheduler, backups, diagnostics) are its natural contents. Per ADR-0009 it is reached
  through numbered development builds `1.0.1` … `1.0.N`, which begin by closing the M4 and M5
  gaps the M6 work depends on. The ladder is planned in `IMPLEMENTATION_STATUS.md`.
