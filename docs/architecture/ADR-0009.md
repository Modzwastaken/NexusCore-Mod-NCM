# ADR-0009 — Development builds: the 1.0.x ladder to v1.5.0

- **Status:** Accepted, amended
- **Date:** 2026-07-26
- **Decided by:** the project owner
- **Amends:** [ADR-0007](ADR-0007.md)
- **Amended by:** [ADR-0010](ADR-0010.md) — a minor line holds exactly five rungs and `x.y.5`
  is a pre-release, after which the minor rolls. The unbounded counter below, and the ✅
  milestone-snapshot mechanism, are superseded.

## Context

ADR-0007 numbers releases `MAJOR.MINOR.0`, advancing by 0.5, and reserves the third component
for patch releases containing "fixes only — no new features and no data-format change".

v1.5.0 is not a small release. Its contents are the M4 and M5 gaps that
`IMPLEMENTATION_STATUS.md` already names as unmet — `ModuleManager`, GameTests, generated
command documentation, the write-ahead journal — followed by M6 economy, M7 chat and
moderation depth, and M8 automation, backups, diagnostics and benchmarks.

Under ADR-0007 as written, all of that lands as one unnumbered jump from `1.0.0` to `1.5.0`.
Nothing between the two is installable, nothing can be run on the three test servers, and
nothing can be named in a bug report. Months of work would sit behind a single version
number, and the first time anyone ran it would be the release.

The owner has decided the intermediate work should be numbered.

## Decision

**The third component is a build counter, not a semantic-versioning patch level.**

| Shape | Meaning |
|---|---|
| `MAJOR.MINOR.0` | A **release**. `1.0.0`, `1.5.0`, `2.0.0`. Carries the ADR-0007 compatibility promise. |
| `MAJOR.MINOR.N`, N ≥ 1 | A **development build** on the road to the next release. May add features, commands and configuration keys. Not a release; not for production. |

Development builds climb `1.0.1`, `1.0.2`, … `1.0.N`. The ladder ends when the accumulated
work is v1.5.0; the final development build and `1.5.0` differ by the version number and the
release ceremony, not by their code.

> **Amended by ADR-0010.** `N` is bounded: a minor line holds exactly five rungs, `x.y.5` is a
> pre-release, and the minor then rolls to `x.(y+1).1`. The ladder is five lines of five.

**What each build contains is planned in `IMPLEMENTATION_STATUS.md`**, under "The road to
v1.5.0", and nowhere else. That document is already the single place unfinished work may be
named (§2.4); a separate roadmap file would be a second place, and the two would drift.

## A number is only assigned to something that works

A build counter is worthless if it counts intentions. A development build is not cut until:

- all three loaders build clean from a clean checkout;
- every test passes;
- `checkstyleMain` and `checkstyleTest` report zero violations;
- `stubMarkerCheck` passes;
- the shared changelog has an entry for that exact version.

The last of those is enforced mechanically by `versionLadderCheck`, a `check` dependency in
the version-owning project. Bumping `mod_version` without writing the changelog entry fails
the build. This is the drift that would otherwise happen every single time.

The other four are the existing gates, already wired.

## Release ceremony: milestone builds only

> **Amended by ADR-0010.** "Milestone build" and "snapshot" are withdrawn. The build that gets
> archived and handed out is `x.y.5`, the **pre-release** at the end of each line — determined
> by the version number rather than by a flag in a table. The three-tier structure below stands;
> only the middle tier's name and trigger changed.

Running the full release checklist on every rung would cost more than the ladder is worth.

- **Ordinary development builds** (`x.y.1`–`x.y.4`) — version bump, changelog entry, all three
  loaders built and tested. No archived jars, no `checksums.txt`, no `release-notes.md` entry.
- **Pre-releases** (`x.y.5`) — additionally archived: all three jars plus checksums, under
  `archived/v<version>/`, labelled a pre-release rather than a release. Immutable, like every
  other archived build.
- **`1.5.0`** — the full `RELEASE_CHECKLIST.md`, including the sign-off table.

`archived/` therefore holds two kinds of thing, and its README says which is which. A
pre-release is what a tester was asked to install; a release is what the public downloaded.

## What this costs, stated plainly

Four things get worse, and hiding them would defeat the point of writing an ADR.

1. **`1.0.1` reads as a patch release and is not one.** Anything parsing this project's
   version as semver will conclude that `1.0.1` is a bug-fix for `1.0.0` and safe to take.
   It is not: it may add commands and configuration keys. Nothing mitigates this completely.
   What mitigates it partly is that only the `x.y.0` shape is ever published, every
   development build's changelog heading says `— development build`, and `archived/` labels
   snapshots as such.

2. **There is no hotfix lane for `1.0.0`.** If a defect is found in the published release
   before `1.5.0`, the fix ships as the next development build, which means taking the
   in-progress feature work with it. This is accepted because `1.0.0` is the only published
   release and nobody is currently depending on a fix-only upgrade path. If that changes
   before `1.5.0`, a lane has to be designed then and this ADR revisited — not improvised
   during an incident.

3. **The ladder is easy to abandon halfway.** A tree sitting at `1.0.7` for a year is worse
   than one sitting at `1.0.0`, because the version implies motion that is not happening.
   `IMPLEMENTATION_STATUS.md` remains the honest record; the build number is not evidence of
   anything on its own.

4. **Every rung makes NeoForge warn on an existing world.** Found by running the thing rather
   than by reasoning about it. Loading `1.0.1` into a world last saved by `1.0.0` produces:

   ```
   [CommonHooks/WP]: The following mods have version differences that were not resolved:
   nexuscore (version 1.0.0 -> 1.0.1)
   ```

   NeoForge compares the mod list recorded in `level.dat` against what actually loaded, and
   NexusCore registers no `DisplayTest` extension point to resolve the difference. It is a
   `WARN`, the world loads normally, and everything works — verified. But a thirteen-rung
   ladder means a tester sees it thirteen times, and a warning that always appears is a
   warning nobody reads. Not fixed here because suppressing it means telling NeoForge that
   version differences do not matter, which will stop being true at `2.0.0`. Recorded so that
   the next person to see it can find out in one search that it is expected.

## What does not change

The ADR-0007 compatibility promise applies to **every rung**, not only to `1.5.0`. A `1.0.x`
build must read a `1.0.0` data directory without operator intervention. Adding fields is
allowed; requiring a migration is not, until `2.0.0`. A development build that cannot open an
existing data directory is a defect in that build, not a licence granted by its version
number.

Every persistent document keeps its own `schemaVersion`, independent of the mod version, so a
data-format change stays detectable regardless of which build wrote it.

## Consequences

- ADR-0007's "**PATCH** (`1.0.0` → `1.0.1`) fixes defects only" no longer holds. That line is
  amended by this ADR; the rest of ADR-0007 stands.
- `mod_version` is bumped at the **start** of a build's work, not at its end, so that anything
  compiled from the tree is labelled with the build it is becoming rather than the release it
  is no longer. Only the tagged commit is the build itself.
- `RELEASE_CHECKLIST.md` gains a development-build section — the short gate above — separate
  from the full release checklist.
- The next release after `1.5.0` is `2.0.0`, and its ladder is `1.5.1`, `1.5.2`, … by the same
  rule.
