# ADR-0010 — Five-rung lines: `.5` is a pre-release, then the minor rolls

- **Status:** Accepted, amended
- **Date:** 2026-07-26
- **Decided by:** the project owner
- **Amends:** [ADR-0009](ADR-0009.md)
- **Amended by:** [ADR-0011](ADR-0011.md) — `1.0.x` became the published patch line for
  release v1.0, so the ladder is **four** development lines (`1.1.x`–`1.4.x`), not five. The
  five-rung line, the `.5` pre-release and the minor-roll rules below are unchanged.

## Context

ADR-0009 made the third version component a build counter and set the ladder climbing `1.0.1`,
`1.0.2`, … with no upper bound and no natural resting point. Two problems followed from that,
and both are the kind that only show up once you try to use the scheme.

A ladder with no bound has no rhythm. Thirteen rungs in one unbroken line means the number
carries no information beyond "later than the one before" — `1.0.11` tells a tester nothing
about how far along the work is or whether it is worth installing.

And ADR-0009's answer to "which builds get handed out" was a **milestone snapshot**: a rung
flagged ✅ in a table. That is a label maintained by hand, in a document, with nothing checking
it. The version number itself said nothing about whether a build was meant for testers.

## Decision

**A minor line holds exactly five rungs, and the fifth is a pre-release.**

| Shape | Meaning |
|---|---|
| `x.y.0` where `y ∈ {0, 5}` | **Release.** `1.0.0`, `1.5.0`, `2.0.0`. Carries the ADR-0007 compatibility promise. |
| `x.y.1` – `x.y.4` | **Development build.** Internal. Built and tested on all three loaders; not handed out. |
| `x.y.5` | **Pre-release.** The line's terminus. Archived, handed to testers, and announced as a pre-release. |
| `x.y.6` and beyond | **Invalid.** The line is full; roll to `x.(y+1).1`. |
| `x.y.0` where `y ∉ {0, 5}` | **Invalid.** Releases only land on `.0` and `.5` minors (ADR-0007). A development line has no `.0`. |

So the ladder to v1.5.0 is five lines of five (**superseded by ADR-0011: four lines,
`1.1.x`–`1.4.x`, because `1.0.x` is now the patch line for v1.0**):

```
1.0.0  release
  1.0.1 … 1.0.4  development     1.0.5  PRE-RELEASE
  1.1.1 … 1.1.4  development     1.1.5  PRE-RELEASE
  1.2.1 … 1.2.4  development     1.2.5  PRE-RELEASE
  1.3.1 … 1.3.4  development     1.3.5  PRE-RELEASE
  1.4.1 … 1.4.4  development     1.4.5  PRE-RELEASE
1.5.0  release
```

Twenty-five rungs and five pre-releases, landing exactly on `1.5.0`. The same shape then runs
`1.5.1` … `1.9.5` to reach `2.0.0`.

**`1.1.0`, `1.2.0`, `1.3.0` and `1.4.0` never exist.** Those minors are development lines, and a
development line has no `.0` rung, because `.0` means released and they are not.

## What this buys

**The version number now answers "should I install this?" on its own.** A tester reading
`1.2.5` knows it is a pre-release without consulting a table. A tester reading `1.2.3` knows it
is internal. Under ADR-0009 both questions needed `IMPLEMENTATION_STATUS.md` open alongside.

**A line is a unit of work with a deadline.** Five rungs is a budget. Work that will not fit
gets split across lines deliberately, at planning time, rather than by letting a counter run.
The exhaustion failure ADR-0009 worried about — "a tree sitting at `1.0.7` for a year" — cannot
happen in this shape, because `1.0.7` is not a legal version.

**"Which builds get archived" stops being a hand-maintained flag.** It is `x.y.5`, mechanically.
The ✅ Snapshot column ADR-0009 introduced is withdrawn, and the term *snapshot* is retired in
favour of *pre-release*.

## What this costs

1. **The five-rung budget is arbitrary, and work does not respect it.** A line whose work needs
   six rungs has to either compress two pieces into one rung or push one into the next line.
   Both are worse than the honest thing, which is to say so in `IMPLEMENTATION_STATUS.md` and
   let the line be uneven. The budget is a planning aid, not a fact about the work.

2. **A pre-release is a promise to hand something out.** `x.y.5` is archived and given to
   testers. If a line ends with nothing worth installing, the pre-release is ceremony with no
   content. When that happens the honest move is to record it — an archived build nobody was
   asked to run is a lie in the archive.

3. **The `.0`-only-on-`.0`-and-`.5`-minors rule is not obvious** from looking at a version
   string, and someone will eventually write `1.2.0` meaning "the start of the 1.2 line". The
   gate rejects it with an explanation rather than letting it through.

4. **It compounds ADR-0009's semver problem rather than fixing it.** `1.1.1` still reads as a
   patch release to any tool parsing this as semver, and now the minor moves too, so `1.2.0`
   looking legal-but-forbidden is a new wrinkle. Unchanged mitigation: only `x.0.0` and `x.5.0`
   are ever published, and every other build says what it is in its changelog heading.

## Enforcement

`versionLadderCheck` enforces every row of the table above, and each rule is proven to fail as
well as to pass. It rejects a sixth rung, a `.0` on a non-release minor, a development build
whose changelog heading does not say so, a pre-release whose heading does not say so, and a
release whose heading claims to be either.

The label a heading must carry is now three-valued: `development build`, `pre-release`, or
neither for a release.

## Consequences

- ADR-0009's ✅ **Snapshot** column and the term *snapshot* are withdrawn. `archived/` holds
  releases and pre-releases.
- `RELEASE_CHECKLIST.md` renames its middle ceremony from "milestone snapshot" to "pre-release"
  and keys it to `x.y.5` rather than to a flag in a table.
- The ladder in `IMPLEMENTATION_STATUS.md` is re-planned into lines of five — four of them,
  per ADR-0011.
- ADR-0009's rule that `mod_version` is bumped at the **start** of a rung's work is unchanged.
