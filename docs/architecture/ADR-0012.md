# ADR-0012 — The version scheme: `x.y.0` is a version, `x.y.1`–`x.y.5` are its builds

- **Status:** Accepted
- **Date:** 2026-07-26
- **Decided by:** the project owner
- **Supersedes:** [ADR-0010](ADR-0010.md), [ADR-0011](ADR-0011.md)
- **Supersedes the numbering in:** [ADR-0009](ADR-0009.md)

## Context

Three ADRs in one day, each amending the one before, produced a scheme with two kinds of minor,
version strings that looked ordinary but were illegal (`1.1.0`), and a four-line ladder capped at
twenty rungs. None of that was asked for. It accumulated because each ADR solved the problem the
previous one had just created, and nobody stopped to state the whole rule in one place.

The owner has now specified the standard directly. This ADR states it once, completely, and
retires the rest.

## Decision

| Shape | Meaning |
|---|---|
| `x.y.0` | **A version.** `1.0.0`, `1.1.0`, `1.2.0`, … The numbered milestone that the builds after it patch. |
| `x.y.1` – `x.y.5` | **A build** of that version: a hotfix or a pre-release. |
| `x.y.6` and beyond | **Invalid.** Five builds fill a version; move up to `x.(y+1).0`. |

The sequence is therefore a single unbroken line:

```
1.0.0   version   (released)
  1.0.1  1.0.2  1.0.3  1.0.4  1.0.5      builds
1.1.0   version
  1.1.1  1.1.2  1.1.3  1.1.4  1.1.5      builds
1.2.0   version
  …
```

**At least five builds before moving up.** `1.0.5` is followed by `1.1.0`, never by `1.0.6`.

**Every minor behaves identically.** There is no special minor, no minor that lacks a `.0`, and
no rule that depends on whether a minor is "a release line" or "a development line".

## What this retires

- **ADR-0010's "a development line has no `.0` rung".** Withdrawn. `1.1.0` exists and is a
  version. This was the single most confusing rule in the old scheme — it made a perfectly
  ordinary-looking version string illegal.
- **ADR-0010's `.0`/`.5`-minors-only rule.** Withdrawn. Minors advance by one.
- **ADR-0011's release-line / development-line split.** Withdrawn. One kind of minor.
- **ADR-0009's "development build" as a distinct kind of thing.** Folded into *build*. A build is
  a hotfix or a pre-release; the changelog heading says which.

ADR-0009's two surviving contributions stand: `mod_version` is bumped at the **start** of a
build's work, and the numbering is enforced mechanically rather than remembered.

## Reaching v1.5.0

[ADR-0007](ADR-0007.md)'s feature-release target is unchanged — v1.5 is still where the economy,
chat, scheduler and backups land. The route there is now simply the sequence above:

```
1.0.0 → 1.0.1 … 1.0.5 → 1.1.0 → 1.1.1 … 1.1.5 → 1.2.0 → … → 1.4.5 → 1.5.0
```

`1.1.0` through `1.4.0` are intermediate versions on the way, not feature releases in the
ADR-0007 sense. Whether any individual version is published to the public is a per-version
decision, recorded with that version — the number does not decide it.

This also removes the twenty-rung ceiling ADR-0011 introduced, and with it the problem that M7
and M8 were crushed into one over-subscribed line. The sequence is open-ended: if the work needs
another five builds, it takes another minor.

## What it costs

1. **`1.0.1` still reads as a semver patch and is not necessarily one.** A build may be a
   pre-release carrying new work, not only a fix. Unchanged from ADR-0009, and unchanged in its
   mitigation: the changelog heading says `hotfix` or `pre-release`, and the gate enforces it.

2. **`x.y.0` does not by itself mean "published".** `1.1.0` is a version bump that may never be
   handed to anyone. Readers who assume `.0` means public will be wrong. The changelog entry for
   each version states whether it was published.

3. **Five is arbitrary.** Work does not arrive in fives. A version whose work needs six builds
   must either compress or roll early with fewer than five — and the "at least five" rule means
   rolling early is the exception, recorded when it happens.

## Enforcement

`versionLadderCheck` enforces every row of the table, and each rule is proven to fail as well as
to pass:

- `mod_version` is exactly `MAJOR.MINOR.PATCH`, whitespace included — the raw property, never a
  trimmed copy, because the build ships what the file literally contains.
- The shared changelog has an entry for exactly this version, outside any fenced code block.
- A build's heading says `hotfix` or `pre-release`; a version's heading says neither.
- The third component never exceeds 5.
- The version is not one already sitting in `archived/`, which is immutable.

## Consequences

- The ladder in `IMPLEMENTATION_STATUS.md` is re-planned onto this sequence.
- `RELEASE_CHECKLIST.md` keys its ceremonies to *build* (`x.y.1`–`x.y.5`) and *version*
  (`x.y.0`) rather than to the retired three-tier vocabulary.
- `archived/` holds versions and any build that was handed to somebody.
- The v1.0.0 security patch keeps the number `1.0.1`; it was already correct under this scheme.
- The versioning work itself becomes `1.0.2`, the next build in the `1.0` line.
