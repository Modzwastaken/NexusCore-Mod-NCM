# ADR-0013 — A redo journal of intent for multi-file transactions

- **Status:** Accepted
- **Date:** 2026-07-27
- **Milestone:** M2 (the gap it left), prerequisite for M6
- **Required by:** §11.1
- **Builds on:** [ADR-0006](ADR-0006.md) (JSON documents, not a platform config system)

## Context

`JsonStore.write` replaces one document atomically: serialise to `.tmp`, fsync, `ATOMIC_MOVE`
over the target. A crash leaves the old file or the new one, never a half-written one. That is
tested and has held since M2.

It says nothing about **two** documents. An economy transfer debits `accounts.json` and appends
to `ledger.json`; a shop purchase moves money and moves items. Written with the tools that exist
today, that is two atomic writes with a window between them:

```
write(accounts.json)   ← succeeds
                       ← crash, power loss, kill -9, OOM
write(ledger.json)     ← never happens
```

Afterwards both files are individually well-formed and internally consistent. Nothing in the mod
can detect that they disagree, because the only record of the operation that connected them was
in the heap of a process that no longer exists. The money is gone from one account and never
arrived in the other — or, on the other ordering, arrived twice.

§11.1 asks for a write-ahead journal for exactly this. M2 recorded it as a real gap, `planned`,
with the note that it is "the first thing M6's economy will need". This ADR decides its shape.

## Decision

**A redo journal of intent, in the data directory, replayed at startup before any module reads
data.**

A transaction stages each document to `<target>.txn-<id>` beside its target and forces it to
disk. It then writes one record — `journal/<id>.json`, naming every target, its staging file and
that file's SHA-256 — and forces it. **That record becoming durable is the commit point.** Only
then are the staged files moved into place, and only then is the record deleted.

`JournalService.replayPending()` runs inside the `storage` module's start. A record that still
exists means the process died between committing and finishing, so it is re-applied and cleared.

Three properties follow, and they are the reason for the shape:

- **Recovery goes forward, not backward.** A committed transaction completes; it is never undone.
- **Replay is idempotent by construction.** A staged file that is gone was already moved, so
  applied entries are skipped. The progress marker and the work it records are the *same*
  filesystem operation, so they cannot disagree — which is what makes crashing *during recovery*
  no different from crashing during the first attempt.
- **Verification precedes application.** Staged bytes that do not match their recorded hash are
  refused, not applied.

## Rationale

### Why redo rather than undo

An undo journal records the *old* contents and rolls a torn transaction back. Both designs
restore consistency, and the difference is which answer a player already has.

By the time a transaction commits, the command has usually told someone it worked. Rolling back
means the server quietly disagrees with a message a player has already read — the money left
their screen and came back, with no record of why. Rolling *forward* honours what the player was
told. Redo also survives the case undo cannot: if the old contents are only in the journal and
the journal is what got corrupted, undo has nothing to restore from, while redo's staged files
are the new contents and are hash-verified before use.

### Why not one combined document

If everything that must change together lived in one file, `JsonStore.write` would already be
enough. That works until the set is `accounts.json` + a ledger that grows forever: every transfer
would rewrite the entire transaction history, turning an O(1) append into an O(n) rewrite, and
forcing unrelated data to share a schema version and a corruption blast radius. The economy
would be one file that gets slower every day it is used.

### Why not an embedded database

SQLite or H2 would give real transactions with none of this code. It is the strongest
alternative, and it was rejected for the reason ADR-0006 rejected a second configuration system:
it is a second storage mechanism. Half the data would be inspectable JSON in the data directory
and half would be opaque to every tool an operator has, backups would need both, and SQLite adds
a native dependency to a mod that currently has none (`THIRD_PARTY_NOTICES.md` records that no
NexusCore capability is native). The journal is roughly three hundred lines and touches nothing
outside the storage package.

### Why not a lock

Locks provide mutual exclusion between threads. The failure here is not concurrent access — it
is a process that stops existing between two writes, and no lock survives that.

### Why hash the staged files

The staged file is fsynced before the record is written, so in the ordinary case the hash always
matches. It is recorded for the case that is not ordinary: filesystem damage, a partial write on
a filesystem whose fsync lied, or an operator who edited a file in the data directory while the
server was down. Applying unverified bytes over good data on the strength of a filename is how a
recovery mechanism becomes the thing that destroys the data.

### Why refusing to start is the right failure

If a staged file fails verification, recovery throws and the server does not start. That is
severe, and it is deliberate. The alternative is completing part of a committed money transfer
and continuing — which produces exactly the corruption the journal exists to prevent, with the
added insult that the mechanism responsible reported success. The record is left in place, so
nothing is lost: an operator repairs or removes the staged file and the transaction retries. This
is the same reasoning that makes `JsonStore` quarantine a corrupt document rather than replace it
with defaults, and §11.1's "never silently discard".

## What this gives up

- **No cross-directory or cross-filesystem transactions.** Staging files sit beside their targets
  so the move is atomic, which requires one filesystem. Everything NexusCore writes lives under
  one data root, so this is not a live constraint, but it is a real limit on the design.
- **No isolation.** This is atomicity and durability, not the I in ACID. A reader between two
  commits sees committed data, but two concurrent transactions on the *same* target race exactly
  as two `JsonStore.write` calls would. Adding isolation would mean a lock manager, which is a
  much larger decision and is not what §11.1 asks for.
- **Write amplification.** Every document in a transaction is written twice — once staged, once
  moved — and fsynced. For the transaction sizes this is built for, the durability is the point.
- **The journal cannot protect what does not go through it.** A caller that writes two files with
  two `JsonStore.write` calls gets the old behaviour and no warning. Nothing mechanical prevents
  that; it is a review matter, and it is why the class javadoc says which tool to reach for.

## Consequences

- `JsonStore`'s `move`, `force` and `forceDirectory` are package-private rather than private, so
  the journal reuses the atomic-move protocol rather than carrying a second implementation of it.
- The `storage` module now recovers before it publishes its services. Module ordering already
  guarantees that everything else starts after it, so no other module can observe a torn state.
- A transaction id may contain only `[A-Za-z0-9._-]` and at most 64 characters, because ids become
  file names. `PathSafety` would catch an escape anyway; refusing early names the actual mistake.
- Document names may not contain `.txn-`. Recovery deletes leftover files by that marker, and a
  target carrying it would be real data caught in the sweep.
- 1.2.2's idempotency keys have somewhere to live: `begin(id)` takes a caller-supplied id, so an
  operation that already has a meaningful identifier can name its own transaction. Deduplicating
  repeated ids is *not* implemented here — that is 1.2.2's work, and this ADR only ensures it is
  not designed out.
- The journal has no production caller at the time of this decision. It is proven by `JournalTest`
  and has never run on a live server, which `IMPLEMENTATION_STATUS.md` records against the row.
