# ADR-0003 — Server-side message resolution for vanilla clients

- **Status:** Accepted
- **Date:** 2026-07-25
- **Milestone:** M0 (decision), implemented by `MessageService` in M1
- **Required by:** §3.1, §6.1, §2.3 part 6, M1

## Context

§3.1 makes server-only operation the defining scope decision for v0.1: *"Players join with
an unmodified vanilla client."* §6.1 makes that mode supported forever, not degraded.

Minecraft resolves `TranslatableComponent` **on the client**, against the language files
the client has loaded. A vanilla client has never seen `assets/nexuscore/lang/en_us.json`,
because it does not have NexusCore installed. So a server-only mod that sends
`Component.translatable("commands.nexuscore.version", …)` displays this to the player:

```
commands.nexuscore.version
```

This is not a rare edge case. It is what **every** player sees in the entire v0.1 and v0.5
release window. It also affects the dedicated-server console, whose `Language` instance
loads only vanilla's `assets/minecraft/lang/en_us.json` and returns the key unchanged for
anything it does not know.

Meanwhile §2.3 part 6 requires an `en_us.json` key for every player-facing string, and §6.2
requires real translatable components once a NexusCore client exists from v1.0.

Both requirements are correct, and naively satisfying the second breaks the first.

## Decision

**Messages are resolved on the server, against NexusCore's own catalogue, and delivered as
already-rendered components.**

1. `MessageService` (M1) owns a catalogue loaded from the bundled
   `assets/nexuscore/lang/en_us.json`, overlaid with the operator's
   `config/nexuscore/messages/en_us.json` (Appendix C).
2. Call sites always name a **key** and pass typed named placeholders. Call sites never
   hold literal player-facing text.
3. Delivery renders the key server-side into a component and sends that. The recipient
   needs no NexusCore installation, no resource pack, and no language file.
4. An unknown key renders safely and visibly — the key itself plus its arguments, never a
   crash and never an empty message (§1.3 "fail safely").
5. From M9, when the handshake (§6.3) confirms a NexusCore client, delivery **may** send a
   real translatable component so the client can localise it. That is a negotiated
   upgrade, never an assumption.

## M0 interim state

M0 permits exactly one command and no services, so `MessageService` does not exist yet.
`NexusVersionCommand` therefore sends a literal component built from a format-string
constant.

To keep that from becoming a second source of truth, the constant and the `en_us.json`
value are asserted equal by `NexusVersionCommandTest.formatStringMatchesLanguageFile`. The
key exists, the wording lives in the language file, and adopting the key in M1 cannot
silently change what players see. This is recorded in `IMPLEMENTATION_STATUS.md`.

## Consequences

- The bundled `en_us.json` is a **server-side** catalogue first and a client resource
  second. It ships in the JAR either way.
- Per-player locale selection is possible later — the server knows each player's locale —
  but it is not in scope for v0.1 and is not claimed anywhere.
- Any future call site that builds player-facing text with string concatenation instead of
  a catalogue key is a defect, because it cannot be translated or overridden by the
  operator.
