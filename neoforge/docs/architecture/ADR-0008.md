# ADR-0008 — Multi-loader architecture: NeoForge, Fabric, and Forge

- **Status:** Accepted
- **Date:** 2026-07-26
- **Supersedes:** the single-loader assumption in §4.1 and §18.2

## Context

v1.0 shipped for NeoForge only. The owner asked for Fabric and Forge builds so the first
release covers all three loaders on Minecraft 1.21.1.

Measured before deciding anything: of 24 source files, **22 touch no loader API at all** —
14 are pure Java and 8 use only vanilla Minecraft classes. Only the `@Mod` entry point and
the flight controller are loader-specific. The port was therefore never a code problem; it
was a build problem.

## Decision

### Three independent Gradle builds, sharing source

```
NexusCore/
├── neoforge/   NeoGradle 7.1.38   Gradle 9.2.1   <- owns the shared sources in src/main/java
├── fabric/     Loom 1.15.4        Gradle 9.2.1
├── forge/      ForgeGradle 6.0.54 Gradle 8.10.2
└── <loader>server/                              <- one test server per loader
```

`fabric/` and `forge/` add `../neoforge/src/main/java` and `../neoforge/src/main/resources`
to their own source sets, excluding the two NeoForge-only files. Every loader compiles the
same source files with its own toolchain.

### Why not a `common` subproject that the others depend on

Because it cannot work, and this was proven rather than assumed. Disassembling
`FlightController.class` from the two shipped jars:

```
NexusCore-neoforge-…jar  setFlight(net.minecraft.server.level.ServerPlayer, boolean)
NexusCore-fabric-…jar    setFlight(net.minecraft.class_3222, boolean)
```

Same source file, different bytecode, different size. The Fabric jar's manifest declares
`Fabric-Mapping-Namespace: intermediary`. There is **no single set of compiled classes both
loaders can consume**, so `project(':common')` as a `java-library` is impossible — and a
plain `java-library` would have no Minecraft on its compile classpath to begin with. Shared
code must be *source*, compiled once per loader.

### Why independent builds rather than one multi-project

**ForgeGradle 6.0.54 refuses to apply on Gradle 9:** *"Found Gradle version Gradle 9.2.1.
Versions Gradle 9.0 and newer are not supported yet."* NeoGradle and Loom are both fine on
9.2.1.

In a single multi-project every module shares one wrapper, so supporting Forge would mean
dragging NeoForge and Fabric back to Gradle 8 — downgrading a shipped, working release to
accommodate a new one. As separate builds each project has its own wrapper and Forge sits on
8.10.2 alone. This is the deciding argument for the layout.

### One source of truth for versions

`neoforge/gradle.properties` holds every version. `fabric/build.gradle` and
`forge/build.gradle` read it with `Properties.load`. Duplicating versions per loader is how a
release ends up with three jars claiming different Minecraft versions.

### Artifact naming

`NexusCore-<loader>-<modVersion>-<mcVersion>.jar`, e.g. `NexusCore-fabric-1.0.0-1.21.1.jar`.
The filename is the only thing an operator sees before installing, and the three jars are not
interchangeable.

## The loader differences that are real

Everything else is a package rename. These three are behavioural and are documented for
operators rather than hidden:

| | NeoForge | Fabric | Forge |
|---|---|---|---|
| Entry point | `@Mod` class | `ModInitializer` (`main`) | `@Mod` class |
| Flight | `creative_flight` **attribute** | `Abilities.mayfly` | `Abilities.mayfly` |
| Metadata | `neoforge.mods.toml`, `type = "required"` | `fabric.mod.json` | `mods.toml`, `mandatory = true` |

**Flight is the one genuine capability gap.** NeoForge's attribute modifiers are additive and
keyed per-mod, so NexusCore can revoke only its own grant and coexists with other flight mods.
Neither Forge (verified: `ForgeMod` registers no such attribute) nor Fabric has an equivalent,
so both write a single boolean where the last writer wins. `MayflyFlightController` is shared
by those two and refuses to clear the flag for creative/spectator players, which is the only
safe mitigation available.

## Two defects this structure already caught, both invisible to the compiler

1. **Fabric did nothing in singleplayer.** A `server` entrypoint with
   `DedicatedServerModInitializer` fires only on a *dedicated* server. Singleplayer and LAN
   run an integrated server, so the mod loaded, listed itself, and was silent. Fixed by using
   `ModInitializer` / `main`.
2. **Forge rejected the jar outright.** Dependency blocks copied from the NeoForge metadata
   produced `Missing required field mandatory in dependency`.

Neither could fail a compile, and neither would be caught by any test running against a
dedicated NeoForge server. Both now have regression tests in their own loader's project
(`FabricEntrypointTest`, `ForgeMetadataTest`), and **each loader has its own test server**,
because the only thing that reliably finds this class of defect is running the packaged jar
on the real loader.

## Consequences

- A shared-code change must be built on all three before release. Each build is independent,
  so nothing enforces this automatically — the release checklist does.
- Adding a loader means one entry point, one metadata file, one build file, one test server.
- The Gradle version skew between projects is deliberate and documented in
  `forge/settings.gradle`; it should be removed when ForgeGradle supports Gradle 9.
